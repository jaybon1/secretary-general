# 비서 업데이트

비서 자신의 일이라 비서가 직접 한다. 단계가 끝날 때마다 한 줄로 진행을 남긴다(예: "6단계 중 3단계 끝 · 다음: 사용자 수정 찾기").

- **사용자 폴더**: 지금 비서 폴더(이 세션이 열린 폴더). **받은 저장소**: 2단계에서 임시 폴더에 받은 최신판.
- 기계적인 일은 받은 저장소의 `scripts/update.mjs`가 한다. 언제나 받은 저장소 쪽 스크립트를 쓴다(사용자 폴더의 옛 버전에는 없거나 옛것이다).
- 건드리지 않는 것: 기억 DB(`secretary.db*`), `models/`, `node_modules/`, `*.local.*`, 키, `backups/`, 작업 공간(`workspaces`, 비서 폴더 밖). 스크립트도 이것들은 읽거나 쓰지 않는다.
- 명령은 PowerShell로 돌린다. 아래 `<…>`는 실제 경로로 바꾼다.

## 1. 백업

1. 기억 DB: 사용자 폴더에서 `node src/cli.ts backup`. 출력의 백업 파일 경로를 적어 둔다.
2. 폴더 사본은 2단계에서 받은 스크립트로 만든다(아래 2단계 끝).

## 2. 최신판 받기

1. `git --version`으로 git이 있는지 본다. 없으면 멈추고 Git for Windows(https://git-scm.com)를 설치해 달라고 한다(비서 설치 조건이라 보통 있다).
2. 이미 받은 저장소가 있으면(처음 붙여 넣는 업데이트 글로 받았으면) 그 폴더를 쓴다. 없으면 `git clone https://github.com/jaybon1/secretary-general "$env:TEMP\secretary-update-<날짜시각>"`. 사용자가 다른 주소를 알려 주면 그 주소로 받는다.
3. 폴더 사본: `node <받은 저장소>\scripts\update.mjs backup --user <사용자 폴더>`. 출력 끝의 `WORK=<백업 폴더>`를 적어 둔다(`backups\update-<날짜-시각>\`, 그 안 `files\`가 사본).

## 3. 버전 판별

`node <받은 저장소>\scripts\update.mjs detect --user <사용자 폴더> --repo <받은 저장소>`

- `VERSION` 파일이 있으면 그 값이 기준 버전이다(v7부터 있다).
- 없으면 사용자 파일을 각 버전(tag)의 파일과 비교한 일치율로 고른다. 출력의 버전별 일치율을 사용자에게 그대로 보여 준다.
- `CLEAR=no`(1등과 2등이 5%p 안이거나 1등이 50% 미만)면 진행하지 말고 어느 버전을 받았었는지 묻는다(선택지: 일치율 위 두세 버전, 마지막은 "기타 (직접 입력)").
- 기준 버전이 최신과 같으면 4단계 plan을 돌려 "이미 최신이에요"가 나오는지 본다. 나오면 "이미 최신이에요(<버전>)"라고 말하고 받은 저장소를 지우고 끝낸다.

## 4. 사용자 수정 찾기

`node <받은 저장소>\scripts\update.mjs plan --user <사용자 폴더> --repo <받은 저장소> --base <기준 버전>`

파일마다 무엇을 할지 나온다(아직 아무것도 바꾸지 않는다):
- 사용자가 안 고친 파일 → 새 버전으로 바꿈. 새 버전에서 생긴 파일 → 추가. 새 버전에서 없어졌고 사용자가 안 고친 파일 → 지움.
- 사용자가 고쳤고 새 버전은 그대로인 파일 → 그대로 둠. 사용자가 지운 파일도 새 버전에서 안 바뀌었으면 지운 채로 둔다("변경 없음"에 들어감).
- 둘 다 고친 파일 → 3방향 합치기(`git merge-file`, 기준 = 기준 버전, 우리 = 사용자, 그들 = 최신).
- 물어볼 것: 새 버전에서 지운 파일을 사용자가 고쳤음, 사용자가 지운 파일이 새 버전에서 바뀜, 새 파일과 같은 이름의 사용자 파일이 있음.

목록을 짧게 요약해 보여 준다(바꿈 N개, 합침 N개, 물어볼 것 N개와 파일 이름). 사용자가 고친 파일 목록은 꼭 보여 준다.

## 5. 합치기

`node <받은 저장소>\scripts\update.mjs apply --user <사용자 폴더> --repo <받은 저장소> --base <기준 버전> --work <백업 폴더>`

- 깨끗이 합쳐지는 것은 바로 적용된다. 부딪힌 파일과 물어볼 파일은 사용자 파일을 그대로 두고 "남은 부딪힘"으로 나온다. 둘 다 고친 파일의 합친 안(부딪힌 곳에 `<<<<<<< 내 것` / `=======` / `>>>>>>> 새 버전` 표시)은 `<백업 폴더>\conflicts\`에 있다.
- 남은 부딪힘마다 질문을 하나씩 쓴다(AGENTS.md의 질문 규칙: 질문 기호 A, B…, 선택지 1, 2…, 마지막은 "기타 (직접 입력)", 추천에 "(추천)"). 맥락 없이 읽어도 알 수 있게, 파일 이름과 부딪힌 곳마다 "내 것"과 "새 버전"의 차이를 한두 줄로 풀어 쓴다. 선택지:
  1. 내 것 유지 (`--take mine`). 둘 다 고친 파일이면 부딪힌 곳만 내 것으로 하고, 같은 파일의 나머지 새 변경은 들어간다. 그 밖(새 버전이 지운 파일 등)은 사용자 파일을 그대로 둔다.
  2. 새 버전으로 (`--take new`). 둘 다 고친 파일이면 부딪힌 곳만 새 버전으로 하고 사용자가 고친 나머지는 지킨다. 그 밖은 새 버전 파일로 바꾸거나, 새 버전이 지운 파일이면 지운다.
  3. 둘 다 살려 합치기 (합친 안이 있을 때만. 비서가 표시를 지우고 두 내용을 다 살린 글로 고친 뒤 `--take edited`)
  추천은 이유와 함께 단다(예: 사용자가 값을 일부러 바꾼 곳이면 1번, 사용자 규칙 한 줄과 새 문장이 같은 자리에 있으면 3번).
- 질문을 보낸 뒤 턴을 끝내고 답을 기다린다. 답을 받으면 파일마다(경로는 apply 출력 그대로) `node <받은 저장소>\scripts\update.mjs resolve --user <사용자 폴더> --work <백업 폴더> --file <경로> --take mine|new|edited`. 3번이면 먼저 `<백업 폴더>\conflicts\<경로>`의 표시를 모두 지운 글로 고친다(표시가 남아 있으면 스크립트가 거절한다).
- 출력 끝 "남은 부딪힘: 없음"이 될 때까지 한다. 끝내 정하지 못한 것은 사용자 파일이 옛 버전 그대로라 새 코드와 맞지 않아 테스트나 비서가 깨질 수 있다. 그렇게 알리고 6단계 보고에 남은 것으로 적는다.

## 6. 마무리

1. apply 출력에 "package.json 바뀜: 예"가 있었으면 사용자 폴더에서 `npm install`.
2. 사용자 폴더에서 `npm test`. 실패하면 실패한 테스트 이름과 첫 오류 줄을 적고, 사용자가 고친 파일 때문인지(4단계 목록) 본다. 고치지 말고 알린다.
3. `node src/cli.ts setup-check`로 설치 점검을 돌려 빠진 항목을 알린다.
4. 보고: 기준 버전 → 새 버전, 새 버전의 바뀐 기능(받은 저장소 `README.md`의 "갈아타기" 절 가운데 기준 버전 다음부터 최신까지의 "바뀐 것"을 묶어 짧게), 그 절들에 파일 바꾸기 말고 사용자가 할 일(자동 시작 다시 등록, 작업 공간·폴더 옮기기 등)이 있으면 그 목록과 함께 할지 묻기, 지킨 사용자 수정 파일, 정한 부딪힘과 남은 부딪힘, 백업 위치(DB 백업 파일, `<백업 폴더>\files`), 테스트 결과.
5. 받은 저장소(임시 폴더)를 지운다. `<백업 폴더>`는 남긴다(되돌릴 때 쓴다: `files\`의 파일을 사용자 폴더에 다시 복사하면 된다).
6. 규칙·훅·도구가 바뀌었으므로 새 세션을 열어 달라고 안내한다(`/clear`나 새 세션). `scripts/remote-server.ps1`이 바뀌었고 비서 서버를 쓰고 있으면, 서버도 다시 켜야 새 것이 쓰인다고 알리고 지금 다시 켤지 묻는다(다시 켜면 서버 안의 세션이 끊긴다).
