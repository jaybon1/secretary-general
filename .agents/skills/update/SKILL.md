# 비서 업데이트

비서 자신의 일이라 비서가 직접 한다. 단계가 끝날 때마다 한 줄로 진행을 남긴다(예: "6단계 중 3단계 끝 · 다음: 사용자 수정 찾기").

- **사용자 폴더**: 지금 비서 폴더(이 세션이 열린 폴더). **받은 저장소**: 2단계에서 임시 폴더에 받은 최신판.
- 기계적인 일은 받은 저장소의 `scripts/update.mjs`가 한다. 언제나 받은 저장소 쪽 스크립트와 스킬을 쓴다(사용자 폴더의 옛 버전에는 없거나 옛것이다). 사용자 폴더의 옛 update 스킬로 시작했고 `backup` 출력에 "이번 업데이트의 순서는 받은 저장소의 스킬에 있어요"가 나오면, 그 파일(받은 저장소의 이 스킬)을 읽고 3단계부터 그 순서를 따른다.
- 이 스킬은 업데이트가 끝날 때까지 받은 저장소의 파일(`<받은 저장소>\.agents\skills\update\SKILL.md`)을 경로로 읽어 따른다. 사용자 폴더의 스킬 자리는 업데이트 중에 바뀐다(v7의 `.claude/skills/`는 실제 폴더, v8부터 스킬 원본은 `.agents/skills/`의 실제 폴더이고 `.claude/skills`는 그리로 가는 연결 하나, 5단계. 공개하지 않은 v8 시험판은 스킬 원본이 `skills/`이고 `.claude/skills/`·`.agents/skills/`에 스킬마다 연결이었다). 받은 저장소의 파일은 업데이트 내내 그 자리에 있다.
- 건드리지 않는 것: 기억 DB(`secretary.db*`), `models/`, `node_modules/`, `*.local.*`, 키, `backups/`, 작업 공간(`workspaces`, 비서 폴더 밖). 스크립트도 이것들은 읽거나 쓰지 않는다.
- 명령은 PowerShell로 돌린다. 아래 `<…>`는 실제 경로로 바꾼다. 아래 명령은 하나씩 따로 돌리고 `;`·`&&`·`if`로 묶지 않는다(특히 저장소 받기와 받은 스크립트 실행).
- 명령이 막히면(권한 거부, Claude Code 자동 모드 판단기의 거부, 승인창에서 거절) 같은 명령을 다시 보내지 않고 다시 시도하자고 추천하지도 않는다. 다른 도구나 다른 방법으로 돌아가지도 않는다. 막힌 명령을 실제 경로로 사용자에게 그대로 주어 직접 돌리게 하고, 다 되면 알려 달라고 한다(받기는 2단계 3번대로, 그 밖의 명령은 출력도 붙여 달라고 한다).

## 1. 백업

1. 기억 DB: 사용자 폴더에서 `node src/cli.ts backup`. 출력의 백업 파일 경로를 적어 둔다.
2. 폴더 사본은 2단계에서 받은 스크립트로 만든다(아래 2단계 끝).

## 2. 최신판 받기

1. `git --version`으로 git이 있는지 본다. 없으면 멈추고 Git for Windows(https://git-scm.com)를 설치해 달라고 한다(비서 설치 조건이라 보통 있다).
2. 이미 받은 저장소가 있으면(처음 붙여 넣는 업데이트 글로 받았거나 사용자가 직접 받았으면) 그 폴더를 쓴다. 없으면 받을 폴더를 실제 경로로 정하고(`$env:TEMP`의 실제 경로 아래 `secretary-update-<날짜시각>`), **저장소 받기만 하는 명령 하나**로 받는다: `git clone https://github.com/jaybon1/secretary-general "<받을 폴더>"`. 받은 스크립트 실행(4번 폴더 사본 등)은 받기가 끝난 뒤 다음 명령으로 따로 돌린다. 받기와 받은 것의 실행을 한 명령에 묶으면 자동 모드 판단기가 위험하다고 막는다. 사용자가 다른 주소를 알려 주면 그 주소로 받는다.
3. 받기가 막히면 다시 시도하지 않고 사용자가 직접 받게 한다.
   - 막혔다고 한 줄로 알리고, 사용자가 PowerShell 창에서 칠 명령을 코드 블록 하나에 실제 경로로 준다: `git clone https://github.com/jaybon1/secretary-general "<받을 폴더>"`. 사용자가 PC 앞이 아니면 PC에서 할 수 있을 때 하면 된다고 함께 적는다.
   - 질문을 하나 하고 턴을 끝낸다: "최신판을 어떻게 받을까요?" 선택지는 1. 위 명령을 직접 실행하고 다 되면 알려 주기 (추천) / 2. 이미 받은 폴더가 있으면 그 경로 알려 주기 / 3. 업데이트 그만두기 / 4. 기타 (직접 입력). 같은 명령을 다시 시도하자는 선택지는 넣지 않는다.
   - 답을 받으면 그 폴더에 `scripts\update.mjs`가 있는지 보고 4번으로 간다.
4. 폴더 사본: `node <받은 저장소>\scripts\update.mjs backup --user <사용자 폴더>`. 출력 끝의 `WORK=<백업 폴더>`를 적어 둔다(`backups\update-<날짜-시각>\`, 그 안 `files\`가 사본).

## 3. 버전 판별

`node <받은 저장소>\scripts\update.mjs detect --user <사용자 폴더> --repo <받은 저장소>`

- `VERSION` 파일이 있으면 그 값이 기준 버전이다(v7부터 있다). 없으면 배포판 파일 목록 `release-files.json`의 버전을 쓴다(v8부터 있다).
- 버전 번호: v0.9.0부터 0.x 세 자리(`v0.가운데.끝`)이고, 그 전의 v1~v8은 0.1.0~0.8.0으로 본다(v8 다음이 v0.9.0). 스크립트가 tag를 이 번호로 줄 세우고 `VERSION`이 `v8`처럼 옛 꼴이어도 그 tag를 찾는다. 출력의 "v8(0.8.0)"처럼 옛 tag에는 0.x 번호가 함께 나오니 사용자에게도 그렇게 보여 준다. `--base`에는 출력의 `BASE=` 값(tag 이름)을 그대로 준다.
- 파일 목록이 있으면 출력에 "목록 N개 중 사용자가 고친 것 M개, 지운 것 K개"와 파일 이름이 나온다(받았던 판의 해시와 비교, git 없이). 4단계에서 사용자가 고친 파일 목록을 보여 줄 때 함께 쓴다.
- 둘 다 없으면(`판별: 못 함`, `CLEAR=no`) 진행하지 말고 어느 버전을 받았었는지 묻는다(선택지: 받은 저장소의 v7 이상 tag, 마지막은 "기타 (직접 입력)"). 이 업데이트는 v7부터 올린다. v7보다 옛 버전이면 그렇다고 알리고 멈춘다.
- 기준 버전이 최신과 같으면 4단계 plan을 돌려 "이미 최신이에요"가 나오는지 본다. 나오면 "이미 최신이에요(<버전>)"라고 말하고 받은 저장소를 지우고 끝낸다.

## 4. 사용자 수정 찾기

`node <받은 저장소>\scripts\update.mjs plan --user <사용자 폴더> --repo <받은 저장소> --base <기준 버전>`

파일마다 무엇을 할지 나온다(아직 아무것도 바꾸지 않는다):
- 사용자가 안 고친 파일 → 새 버전으로 바꿈. 새 버전에서 생긴 파일 → 추가. 새 버전에서 없어졌고 사용자가 안 고친 파일 → 지움.
- 새 버전이 옮긴 파일(받은 저장소 `scripts/update-moves.json`) → 사용자가 안 고쳤으면 새 자리로 옮김, 사용자만 고쳤으면 사용자 내용 그대로 새 자리로. 옛 자리 파일은 지운다. 목록에 "(옛 자리 …)"로 나온다.
- 사용자가 고쳤고 새 버전은 그대로인 파일 → 그대로 둠. 사용자가 지운 파일도 새 버전에서 안 바뀌었으면 지운 채로 둔다("변경 없음"에 들어감).
- **물어볼 것:** 사용자도 새 버전도 고친 파일(옮겨진 파일 포함, 깨끗이 합쳐져도), 새 버전에서 지운 파일을 사용자가 고쳤음, 사용자가 지운 파일이 새 버전에서 바뀜, 새 파일과 같은 이름의 사용자 파일이 있음.
- 사용자 폴더에 `release-files.json`(받았던 판의 파일 목록)이 있으면, 기준 tag와 달라도 목록의 해시와 같은 파일은 사용자가 안 고친 것으로 본다(받았던 판이 tag와 조금 달랐던 경우). 그런 파일 수가 "파일 목록 해시로 사용자가 안 고친 것으로 본 파일"로 나온다. 목록 파일 자체는 언제나 새 버전 것으로 바뀐다.

목록을 짧게 요약해 보여 준다(바꿈 N개, 옮김 N개, 물어볼 것 N개와 파일 이름). 사용자가 고친 파일 목록은 꼭 보여 준다.

## 5. 적용하고 묻기

apply를 돌리기 전에 4단계 plan 출력의 개수로 요약 한 줄을 대화에 남긴다(물어볼 것은 종류를 합쳐서). 예: "적용 전 요약: 바꿈 40 · 추가 12 · 옮김 30 · 지움 3 · 사용자 것 그대로 2 · 물어볼 것 5". 이 줄을 쓰지 않고 apply를 돌리지 않는다.

`node <받은 저장소>\scripts\update.mjs apply --user <사용자 폴더> --repo <받은 저장소> --base <기준 버전> --work <백업 폴더>`

- 스킬 자리(v7이나 v8 시험판에서 올라올 때): apply가 옛 배포판의 스킬 파일을 옛 자리(v7은 `.claude/skills/<이름>/`, v8 시험판은 `skills/<이름>/`)에서 `.agents/skills/<이름>/`으로 옮기고(옮겨진 파일과 같다. 사용자가 고친 것은 고친 내용 그대로), 끝에 옛 자리에 남은 것(사용자가 만든 스킬, 사용자가 더한 파일, 아직 정하지 않은 파일, Ego Lite의 `ego-browser` 연결)도 같은 자리로 옮긴 뒤, **같은 명령 안에서** v8 시험판의 스킬마다 연결을 지우고 `.claude/skills`를 `.agents/skills`로 가는 연결(디렉터리 정션) 하나로 만든다. 옮기기와 연결 만들기를 한 명령에서 하므로 명령 사이에 스킬 폴더가 비는 때가 없다(이 세션이 다시 스킬을 찾거나 새 세션이 열려도 스킬이 있다). 출력의 "스킬 자리"(사용자가 만든 스킬 이름), "옮김: …", "만듦: …"을 보고에 쓴다. 아직 정하지 않은 스킬 파일은 새 자리(`.agents/skills/…`)에 사용자 것 그대로 있고, resolve가 거기서 정한다. "그대로 둠"이나 "실패" 줄이 있으면 6단계의 설치 점검 때 그 폴더를 사용자와 보고 `node src/cli.ts skill-links`로 다시 고친다.
- 한쪽만 고친 파일은 바로 적용된다. 물어볼 파일은 사용자 폴더를 그대로 두고 "남은 부딪힘"으로 나온다. 파일마다 고를 것과 스크립트 추천, 사용자가 고친 내용(`<백업 폴더>\user-diffs\<경로>.diff`, 받았던 버전과 지금 사용자 파일의 차이)이 함께 나온다. 후보 파일은 `<백업 폴더>` 아래에 있다: `keep\`(지금 사용자 파일), `new\`(새 버전), `merged\`(깨끗이 합친 안), `conflicts\`(부딪힌 곳에 `<<<<<<< 내 것` / `=======` / `>>>>>>> 새 버전` 표시가 있는 합친 안), `merged-mine\`·`merged-new\`(부딪힌 곳만 내 것 / 새 버전으로 정한 합친 안).
- 남은 것마다 질문을 쓴다(AGENTS.md의 질문 규칙: 질문 기호 A, B…, 선택지 1, 2…, 마지막은 "기타 (직접 입력)", 추천에 "(추천)"). 맥락 없이 읽어도 알 수 있게, 파일 이름과 무엇을 하는 파일인지, 사용자가 무엇을 고쳤는지(user-diffs를 읽어 한두 줄로), 새 버전이 무엇을 바꿨는지(합친 안이나 `new\`와 `keep\`을 비교해 한두 줄로)를 풀어 쓴다. 선택지(그 파일의 "고를 것"에 있는 것만):
  1. 유지 (`keep`): 내 파일 그대로. 옮겨진 파일이면 내 내용을 새 자리로 옮긴다. 코드 파일(.ts·.ps1·.mjs·.json)은 새 버전의 다른 파일과 안 맞아 깨질 수 있다고 함께 적는다.
  2. 덮어쓰기 (`new`): 새 버전 파일로. 내 수정은 `<백업 폴더>\files`와 user-diffs에 남는다. 새 버전이 지운 파일이면 지운다.
  3. 섞기: 깨끗이 합쳐진 파일은 `merge`(내 수정 + 새 변경). 부딪힌 곳이 있으면 `merge-mine`(부딪힌 곳만 내 것, 나머지는 섞기)과 `merge-new`(부딪힌 곳만 새 버전)를 따로 선택지로 둔다.
  4. 비서가 손으로 섞기 (`edited`, 합친 안이 있을 때만): 비서가 `merged\` 또는 `conflicts\`의 합친 안을 고쳐(표시는 모두 지운다) 두 내용을 다 살린 뒤 `--take edited`.
  5. (여러 파일로 나뉘어 옮겨진 코드 파일) 새 버전으로 두고 내 수정만 옮겨 적기: 그 파일은 `new`(또는 `merge-new`)로 정하고, user-diffs의 내 수정이 새 버전의 어느 파일로 갔는지 찾아(같은 이름·값을 검색) 비서가 그 파일에 옮겨 적는다. 옮겨 적은 파일과 줄을 보고에 적는다. 부딪힌 곳이 파일 대부분을 덮으면(`conflicts\`의 표시 사이가 수십 줄) 이 경우다.
  추천은 스크립트 추천을 그대로 쓰지 말고 이유와 함께 판단해 단다(예: 사용자가 값을 일부러 바꾼 곳이면 섞기, 사용자 규칙 한 줄과 새 문장이 같은 자리에 있으면 손으로 섞기, 나뉜 코드 파일이면 5번, 새 버전에서 쓰지 않는 옛 파일이면 덮어쓰기). 코드 파일에서 부딪힌 곳의 스크립트 추천은 새 버전 쪽(`merge-new`)이다: 내 쪽은 새 코드와 안 맞는 옛 코드일 때가 많기 때문이다.
- 물어볼 것이 4개를 넘으면, 질문들 앞에 묶음 질문 하나를 먼저 둔다: "나머지는 추천대로 할까요?"(1. 예, 아래 추천대로 (추천) / 2. 파일마다 고를게요 / 3. 기타 (직접 입력)). 파일마다의 추천을 한 줄씩 목록으로 함께 보여 준다.
- 질문을 보낸 뒤 턴을 끝내고 답을 기다린다. 답을 받으면 파일마다(경로는 apply 출력 그대로, 옮겨진 파일은 옛 경로로 불러도 된다) `node <받은 저장소>\scripts\update.mjs resolve --user <사용자 폴더> --work <백업 폴더> --file <경로> --take <고른 것>`. "나머지는 추천대로"면, 비서 추천이 스크립트 추천과 다른 파일만 먼저 `--file`로 정하고 `resolve --user <사용자 폴더> --work <백업 폴더> --rest`로 나머지를 스크립트 추천대로 정한다.
- 출력 끝 "남은 부딪힘: 없음"이 될 때까지 한다. 끝내 정하지 못한 것은 사용자 파일이 옛 버전 그대로라 새 코드와 맞지 않아 테스트나 비서가 깨질 수 있다. 그렇게 알리고 6단계 보고에 남은 것으로 적는다.

## 6. 마무리

1. apply 출력에 "package.json 바뀜: 예"가 있었으면 사용자 폴더에서 `npm install`.
2. 사용자 폴더에서 `npm test`. 실패하면 실패한 테스트 이름과 첫 오류 줄을 적고, 사용자가 고친 파일 때문인지(4단계 목록) 본다. 고치지 말고 알린다. 사용자가 직접 만든 `.ps1`(배포판 파일 목록 `release-files.json`에 없는 파일, 목록이 없으면 기능 목록 `features.json`에 없는 파일)의 BOM·구문 문제는 실패가 아니라 `ℹ 경고` 줄로 나온다. 업데이트 탓이 아니니 그 파일 이름과 고치는 법(한글이 있으면 BOM 있는 UTF-8로 저장)만 알린다.
3. 버전을 올릴 때 한 번 하는 옮기기("올린 뒤 할 일"): 받은 저장소 `CHANGES.md`에서 기준 버전 다음부터 최신까지 버전마다의 "올린 뒤 할 일"을 모두 모은다.
   - 먼저 모은 할 일 전체를 번호 그대로 한 줄씩 보여 준다(예: "올린 뒤 할 일 7개: 1. 예약 작업 다시 등록 2. …"). 이 판에 해당 없어 보이는 것도 목록에서 빼지 않는다.
   - 하나도 빼지 않고 번호 순서대로 하나씩 한다. 비서가 할 수 있는 것(파일·DB 옮기기)은 내용을 보여 주고 승인받아 하고, PC 설정(예약 작업 다시 등록, 관리자 PowerShell)은 사용자에게 할지 묻고 명령을 준다.
   - PC 설정(예약 작업, 사용자 설정의 훅·상태줄, 비서 폴더 환경변수)은 한 PC에 비서가 여럿일 수 있다. 예약 작업 이름과 환경변수 이름에는 이 비서의 고유 번호(`.secretary-id`, apply 출력의 "비서 고유 번호")가 붙어 다른 비서와 겹치지 않는다. 바꾸자고 하기 전에 그 설정이 가리키는 폴더가 이 비서인지 본다(`node src/cli.ts setup-check`가 "옛 이름 '…'으로 등록됨"(이 비서 것, 옮길 것), "다른 비서 것을 함께 씀"으로 알린다). 번호가 다르거나 번호가 없는 다른 비서 폴더(지금도 비서가 있는 폴더)를 가리키면 그 비서 것이라 바꾸자고 하지 않는다. 이 비서 폴더 안의 옛 자리, 같은 번호의 다른 폴더(남겨 둔 옛 사본), 비서가 없어진 폴더일 때만 이 비서의 옛 경로다. 옛 이름 예약 작업은 `scripts/tasks/install-tasks.ps1 -Task <id>`가 새 이름으로 옮긴다(비서 서버 작업 `server`는 관리자 PowerShell에서 사용자가 돌린다: 비서 폴더로 `cd` 한 뒤 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts\tasks\install-tasks.ps1 -Task server`). 확인부터 해야 하는 것(예: 등록된 예약 작업이 있는지)은 "하겠다"고만 하지 말고 그 자리에서 명령으로 확인한다.
   - 할 일마다 결과를 한 줄로 남긴다: 함 / 사용자에게 명령 드림 / 사용자가 미룸 / 해당 없음(이유와 확인한 근거, 예: "`Get-ScheduledTask` 결과 등록된 작업 없음"). 건너뛰는 것은 반드시 이유를 말한다.
   - v7에서 올라오면 여기에 큰 일 판 옮기기가 들어 있다(`node src/cli.ts big-work-from-profile <백업 폴더>\big-work-plan.json`으로 미리 보고 → 줄마다 상태가 맞는지 비서가 확인해 그 파일을 고치고 → 사용자에게 보여 승인받아 `--apply`).
   - 할 일을 모두 끝내거나 결과를 남긴 뒤에 4번(설치 점검)과 5번(보고)으로 간다.
4. `node src/cli.ts setup-check`로 설치 점검을 돌려 빠진 항목을 알린다. '스킬'(skills) 항목이 빠졌으면 `node src/cli.ts skill-links --dry-run`으로 보여 주고 `node src/cli.ts skill-links`로 만든다(실제 폴더가 걸리면 지우지 않고 사용자에게 묻는다).
5. 보고: 기준 버전 → 새 버전, 새 버전의 바뀐 기능(`CHANGES.md`에서 기준 버전 다음부터 최신까지의 "새 기능"·"바뀐 것"을 묶어 짧게), 3번의 할 일마다 결과(번호 그대로, 남은 일 포함), 지킨 사용자 수정 파일과 고른 것(유지·덮어쓰기·섞기), 남은 부딪힘, 백업 위치(DB 백업 파일, `<백업 폴더>\files`), 테스트 결과.
6. 받은 저장소(임시 폴더)를 지운다. `<백업 폴더>`는 남긴다(되돌릴 때 쓴다: `files\`의 파일을 사용자 폴더에 다시 복사하면 된다).
7. 규칙·훅·도구가 바뀌었으므로 새 세션을 열어 달라고 안내한다(`/clear`나 새 세션). 비서 서버(`scripts/server/remote-server.ps1`)가 바뀌었고 비서 서버를 쓰고 있으면, 서버도 다시 켜야 새 것이 쓰인다고 알리고 지금 다시 켤지 묻는다(다시 켜면 서버 안의 세션이 끊긴다).
